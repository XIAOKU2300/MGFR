# EFMI → MGFR 独立皮肤适配

把用户指定的 EFMI 资源变成可由目标项目加载的独立模型。先确认具体皮肤、保留的功能与交付边界；已有信息足够时直接工作。当前案例要求保留现有角色的脸、头发、828 根骨骼、40 个形变与 14 材质槽，由用户自己编写换肤功能。

## 执行边界

- 源 Mod、现有模型、正在使用的项目和启动器只读。生成独立的新目录；制作皮肤不自动授权替换角色、改宿主代码或部署。
- 脚本拒绝已有输出目录。失败时保留证据，检查原因后使用新的输出路径；不要清理、覆盖用户文件来重试。服装部件的网格移除只发生在新生成的数据中。
- 不把模型、贴图、原始缓冲、语音或密钥加入 skill、代码提交或公开交付。脚本和结构说明可共享；资源由使用者自行提供。
- 不读取 Mod 管理器的无关私有/不透明元数据，不执行 Mod 内的脚本或着色器二进制。

## 选择路径

**祀蓝白泳装的同一套输入：**先读 [workflow.md](references/workflow.md)，运行 `scripts/port_si.py inspect`。输入指纹匹配后可用 `convert`；`--barefoot` 输出平脚曲面修正候选。脚本检查的正是本案例，不能把它当成任意皮肤转换器。

**不同皮肤、角色、骨架或版本：**先按 [format-and-mapping.md](references/format-and-mapping.md) 重新检查格式、实际 draw ranges、坐标、UV 和绑定关系。复用通用读写/验证工具，重新建立 profile；不要删掉指纹保护后直接运行祀的部件表。

**赤脚、脚踝或小腿返修：**先读 [ankle-review.md](references/ankle-review.md)。处理实际几何、静止骨架、bind pose 与 IK 目标；隐藏鞋子或重算法线不能修复弯折的轮廓。最新 v4 曲面经过模型检查，但尚未获得用户对自然度的确认。

## 工作流程

1. **只读核查。**记录目标项目加载格式、骨骼/形变/材质依赖和用户要求。列出 Mod 的 ini、mesh、DDS，不从目录名推定完整模型。对输入生成 hash 清单。
2. **决定保留范围。**优先保留目标角色已工作的脸、表情和骨架；新身体/衣服需要转移权重与静止姿态。部件按 INI 的实际绘制区间选择，避免把多个体型或隐藏选项同时合并。
3. **新目录转换。**校准坐标、比例、绕序、UV、静止姿态和权重；重建正确的父相对骨骼坐标与 inverse bind。保留名称和索引契约，原始资源保持不变。
4. **结构与渲染双重验证。**先用 `scripts/model_tool.py verify` 检查数据，再按 [unity-verification.md](references/unity-verification.md) 在隔离 Unity 项目渲染。必须打开实际图，检查正/背/侧/斜面、动作和表情；局部改形必须有局部近景。
5. **持续记录与交付。**按 [delivery-contract.md](references/delivery-contract.md) 写简短过程日志，交付原生模型、贴图、皮肤入口、检查报告与真实渲染图。清楚区分结构通过、独立 Unity 渲染、用户视觉确认、正式项目集成和 VR 验证。

## 完成标准

- 输入 hash 不变；输出能够由目标加载器读取，索引、权重、形变、材质、rest/bind 数据一致。
- 目标行为有实际证据：静止 BakeMesh 与顶点一致；动作与表情确实改变几何；贴图、透明层和局部轮廓已看图检查。
- 视觉自然度不能由“脚底距地小于 1 mm”等指标代替。用户否定的版本是失败记录；修正版未获确认时标注待用户评价，不能写成用户已验收。
- 若用户只要文件夹，完成独立资源交付，不自动实现切换功能。

技能包本身的实际复跑范围见 [validation.md](references/validation.md)；它与模型的用户视觉验收分开记录。
