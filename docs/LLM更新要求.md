# MGFR 的 LLM 更新要求

> 适用范围说明：本文记录原私有维护工程和本机运行版本的正式要求。独立源码候选的协作入口是根目录 `AGENTS.md`；导出候选不改变原私有仓库的可见性限制或本机运行要求，也不构成任何 GitHub 上传许可。

状态：正式生效 v1。用户确认日期：2026-10-21。

目的：后续 LLM 接手时保留已经可用的整套项目，按用户反馈做有证据、范围明确的更新。用户已在本次对话中明确确认，后续LLM更新必须遵循本要求。GitHub 的逐版本确认要求已经由用户直接提出，立即生效。

## 1. 只改原入口实际加载的最新版

1. 每次动手先追踪 `H:\MGFR\启动MGFR.cmd` 到启动脚本、主程序、语音进程、动作目录和配置来源，记录实际路径与指纹。
2. 不按目录时间、新旧名称、`Current` 或 `Final` 字样判断最新版。与其他模型同时工作时，应用前再检查文件指纹；发现变化先核对冲突，不覆盖别人的新改动。
3. 只保留原来的一个日常启动入口。普通修复不得新建启动器、换入口、复制一套“正式版”让用户重新配置。
4. 隔离候选和测试产物可以放在检查目录，但不得成为另一套日常运行版本。交付必须说明原入口是否已经实际加载了改动。

## 2. 动作统一以终末地官方源数据为准

1. 所有动作从已核对的终末地官方剧情、对话、待机、行走及互动资源取得，保存来源、片段名、时长、采样率和校验值。
2. 优先复用项目已建立的官方骨骼对应关系。先核对实际模型、绑定姿势、骨架层级、坐标系和播放链；不能只因用户说“已经适配”就跳过核对，也不能忽略已经完成的对应关系再做一遍转换。
3. 禁止凭观感自行添加胸肩后仰、手臂角度、脚踝方向拟合、姿态钳制、全动作压速、额外手臂 IK 或身体避让来掩盖接入错误。
4. 出现踮脚、双臂后移、胸部前挺、穿模或抽搐，先与官方同一帧对照，定位是源片段、坐标/绑定、播放叠加还是模型问题。撤销错误处理，而不是继续叠加补丁。
5. 原动作本来有的抬脚、踮脚、转身和快速动作不得为了通过测试被削平。仅做播放器必要的格式、坐标和骨骼映射；确需改变官方姿态或模型绑定时，先说明证据与具体方案，取得用户针对该改变的同意。
6. 明确区分“官方动作来源”“目标骨架映射播放”和“完整原骨架直接播放”，不能把映射/烘焙结果宣传成完全不经转换的原样播放。
7. 当前脚部问题的已知原因是多加了脚踝到脚趾的方向拟合。泳装待机被额外转了约42度；恢复候选通过后已获用户同意并应用到166份资源。后续不得把这层拟合重新带回。

## 3. 保留全部已确认功能，修改只限本次任务

动作更新不得顺手更改渲染、材质、布料、模型比例、触摸判断、语音参数、服务端口、音色、记忆或其他已经可用的模块。

后续应保持的功能包括：

- 83段保存的动作、两套皮肤的166份动作数据；当前62段允许LLM调用，备用片段不能未经核查直接开放。
- 重点保留可爱、待机、对话、行走、摸头相似反应和有互动感的动作。
- 结构化JSON回复，含台词、情绪、情绪强度、表情变体和动作时间表；支持通用本地接口，并参考近期历史避免过于重复。
- 多类情绪，每类多个表情，情绪表情与身体动作可以同时播放；保持口型、眨眼和注视。当前45个兼容表情与归档的97脸骨资源必须如实区分。
- 台词先进入正常TTS合成和播放流程，动作按实际语音轮次与播放状态同步；保留正常收尾、回待机、打断、取消和下一轮恢复。
- 原ASR/LLM/TTS配置和用户已正常使用的对话链；播放目标是Pico头显。声音异常时核对实际输出设备，不擅自重配整套语音。
- 长期记忆、角色资料、多轮历史、互动事件与说话期间排队、用户开口优先。
- 皮肤切换、服装与鞋子穿脱、布料、手部交互、缩放、手势触控面板、字幕和XR恢复。

以上数量是2026-10-21的本地基线，后续必须先读实际目录和运行接口再报告数量，不能照抄旧文档冒充实时验证。

## 4. 改前核对、改后按问题验证

1. 动手前记录目标路径、当前指纹、影响面和回退方法；按用户当次有效的覆盖/删除协议执行。优先补丁修改，禁止无边界替换、清空目录或强制回退。
2. 应用前保存可恢复备份；并发变化应停止该覆盖、核对差异，不用旧备份覆盖新版本。
3. 动作必须验证源数据和目标结果：通道、时序、采样、四元数、绑定与混合；换肤后也要检查。不能只用“没有异常跳变”证明姿态正确。
4. 脚部要看实际渲染的侧面、前后和鞋/赤脚状态；肩臂要与官方帧及骨骼位置对照；穿模要检查相关网格。不能只看正面截图或脚底最低点就声称正常。
5. 语音相关改动检查真实TTS输出、实际播放状态与动作同步；模拟文本、静音预热或合成事件不能冒充头显听感和真实对话验收。
6. 根据本次改动选择必要测试，通过后停止无理由的重复和扩大测试。桌面检查、合成回放、本地服务验证和头显实测分别标明。
7. 简单重复的资源整理、格式核对和清单检查可按用户授权交给较便宜的模型；核心骨骼方案、最终集成和验收由主模型审阅。不要让模型凭空编造动作或未经审阅直接覆盖主项目。

## 5. 本地完成与GitHub上传是两个阶段

1. 先完成本地修改和必要验证，整理最终候选；不得把尚未完成的实现推给用户“先批准方案再做”。
2. 交付候选时报告：实际入口与版本、改了什么、改动文件、验证结果及范围、仍未验证的部分、资源/配置是否受影响和回退位置。
3. 为候选生成唯一版本标识、Git提交SHA及文件校验清单；本地提交可以用于审阅，但不是上传。
4. 明确询问用户是否同意将这个具体候选上传到指定私人仓库。用户确认本地运行、继续修复、确认覆盖或曾经批准某个旧版本，都不自动等于同意上传新版本。
5. 只有收到用户明确的当次上传许可后，才可push或通过GitHub API写入该版本；不得自动提交远端PR、标签或Release绕过确认。
6. 确认后如有任何新的修改，重新提交最终候选并取得上传许可。禁止强推、改公开、上传凭据和个人记忆。
7. 上传后核对远端提交和私人可见性，给用户仓库链接及提交标识；失败如实报告，不声称已上传。

本次用户“把目前这个项目用私人库上传我的GitHub”的指令，只授权本次基线上传；以后每次版本仍执行上述流程。

## 6. 交付格式

使用简短中文，先说是否完成和实际生效位置，再说明改动、验证和必要限制。出现自己造成的问题，直接说明原因并纠正，不把问题推给官方动作或用户配置。

确认记录：用户在草案交付后回复“确认”，本要求v1正式生效。该确认仅批准更新要求，不授权上传这次文档修改或任何未来版本；GitHub上传仍须按第5节逐版本确认。
